# 해설이 있는 분석 연습: 보이는 증거로 어디까지 말할 수 있을까

> 상태: 검토됨 · 적용 범위: 앞 장의 공식 규약과 로컬 실험을 연결한 연습 · 원천 확인일: 2026-10-04 · 실습 여부: 원천·가상 예시 중심; 연결 실습의 범위는 본문

> **먼저 읽을 장:** [관측 품질](../foundations/time-and-data-quality.md), [어댑터 상태](../product/adapter-contracts.md#수집-상태는-서로-다른-축으로-보존한다). 여기서는 그 구분을 장애 조사에 적용합니다.

## 먼저 이해할 것

장애 분석은 그럴듯한 원인 하나를 빨리 고르는 일보다, 확인한 사실과 아직 모르는 것을 분리하는 데서 시작합니다. 같은 관측으로 여러 원인이 가능하면 다음에 수집할 증거를 정해야 합니다. 이 장의 모든 사건 시각·업무 수치는 학습용 가정입니다.

각 연습의 관측을 읽고 먼저 답을 생각한 뒤 해설과 비교합니다. 원리는 실제 [PostgreSQL 실습](../database/postgresql-concurrency-lab.md), [Kubernetes 실습](../kubernetes/inventory-consistency.md), [HTTP 실습](../network/dns-and-connection-lifecycle.md), [Collector 실습](../product/telemetry-delivery-contracts.md)에 연결됩니다.

## 연습 1: 사용자는 실패를 봤는데 주문은 생성되었다

다음 조건을 가정합니다. client timeout은 DB 문장 취소로 전파되지 않습니다. 서버는 같은 주문 요청의 재전송을 구분하는 멱등성 정책이 없습니다.

| 상대 시각 | 관측 |
| --- | --- |
| 0초 | 주문 요청 접수, DB UPDATE가 다른 트랜잭션의 잠금을 기다림 |
| 3초 | client가 응답 대기를 끝내고 timeout 표시 |
| 3.2초 | 같은 주문 내용을 새 요청으로 재전송 |
| 4초 | 원래 잠금을 가진 트랜잭션 종료, 첫 주문 처리 진행 |
| 이후 | 두 요청이 각각 별도 주문으로 commit됨 |

**생각할 질문:** timeout이 있었는데 왜 첫 주문도 생겼는가? DB CPU가 낮았다는 사실이 DB와 무관하다는 증거인가? timeout을 늘리면 중복 방지가 완성되는가?

**해설:** timeout은 해당 client의 대기 종료입니다. 이 가정에서는 서버 작업 취소가 아니므로 첫 작업이 나중에 commit할 수 있습니다. 잠금 대기는 CPU를 많이 사용하지 않을 수 있어 낮은 CPU만으로 DB 원인을 기각하지 않습니다. timeout 연장은 중복 요청을 식별하는 업무 계약을 대신하지 않습니다.

다음 증거는 요청 ID·업무 키·각 attempt, DB의 state와 wait_event, 차단 관계, commit 시점, client 취소 전파 방식입니다. 동일한 주문의 멱등성 키와 결과 보관·재시도 정책은 [요청 timeout](../application/timeouts-and-retries.md)을 바탕으로 설계합니다.

## 연습 2: DELETED 알림이 왔는데 대상이 살아 있다

수집기는 `environment=production` selector로 객체를 보고 있습니다. 객체 A의 label이 `staging`으로 바뀐 뒤 watch에 DELETED가 나타났습니다. 이름으로 직접 GET하면 200이고 UID도 이전과 같습니다.

**생각할 질문:** 객체가 삭제됐다가 재생성됐는가? 이름이 같으니 이전 대상이라고 판단해도 되는가? 전역 토폴로지에서 즉시 지워도 되는가?

**해설:** 제시된 증거는 selector 집합에서의 이탈과 양립합니다. UID가 유지됐다는 조건까지 보면 이 사례를 이름 재사용의 새 객체라고 설명할 근거가 없습니다. 전역 삭제 대신 이 수집 범위에서 제외된 사건으로 처리하고 다른 관측 범위의 소유 관계를 확인합니다.

추가 조사에서는 watch의 selector와 namespace, UID, 수집 권한, 재동기화 상태를 함께 기록합니다. [인벤토리 실습](../kubernetes/inventory-consistency.md)에서 같은 종류의 현상을 실제 ConfigMap으로 확인했습니다.

## 연습 3: 오류율이 10%와 52.63%로 다르다

metric은 전체 요청 10,000개 중 오류 1,000개라고 집계했습니다. trace 저장 정책은 오류 1,000개를 모두 남기고 정상 요청 중 900개만 남깁니다. 두 원천 모두 주어진 가상 입력을 정확히 세었다고 가정합니다.

**생각할 질문:** 어느 수집기가 잘못됐는가? trace가 더 자세하므로 52.63%를 SLO에 사용하면 되는가?

**해설:** 집합이 다릅니다. metric의 질문은 전체 요청의 오류 비율이고 trace의 질문은 선택해 보관한 자료의 오류 비율입니다. `1,000/10,000=10%`, `1,000/1,900≈52.63%`가 각각의 답입니다. 자세한 기록이라는 이유로 전체 모집단을 더 잘 대표한다고 판단할 수 없습니다.

먼저 집계 대상·구간·오류 정의·sampling·전송 유실을 맞춥니다. 이어서 [sampling과 모집단](../application/trace-sampling-and-context.md)의 규칙으로 화면 이름과 SLO 입력을 명세합니다.

## 연습 4: 성공 응답은 늘었는데 일부 trace가 없다

앱은 Collector에 전송해 HTTP 200을 받았습니다. Collector의 목적지에서는 부분 성공으로 span 일부를 거절했습니다. 다른 요청에서는 목적지가 본문을 받은 뒤 응답 연결이 끊겨 같은 span ID가 다시 들어왔습니다.

**생각할 질문:** 앱이 받은 200 수를 최종 저장 성공 수로 써도 되는가? 목적지 수신량에서 거절량을 빼면 언제나 고유한 저장 항목 수가 되는가?

**해설:** 수용 경계와 신호 단위가 다릅니다. HTTP 요청 하나가 여러 span을 담을 수 있고, 부분 거절과 중복 재전송도 있습니다. 고유 항목 수를 계산하려면 안정적인 항목 식별과 중복 처리, 실제 저장 완료 정보가 필요합니다. 수신량·전송 시도량·거절량의 단위와 시간 범위를 맞춰야 합니다.

이번 책의 [Collector 실습](../product/telemetry-delivery-contracts.md)은 이 전송 현상을 확인했지만 목적지의 영속 저장은 검증하지 않았습니다. 학습용 실험의 관측 범위를 실제 저장 보장으로 확대하지 않는 연습이기도 합니다.

## 조사 메모를 완성하는 양식

다음은 **분석 기록 제안**입니다. 원인을 아직 확정하지 못했어도 정확한 기록을 만들 수 있습니다.

| 항목 | 기록 예시 |
| --- | --- |
| 질문 | 어떤 요청 집합의 지연이 늘었는가? |
| 확인 사실 | 같은 backend의 active·Lock과 blocker를 함께 관측 |
| 시간·범위 | 특정 인스턴스·실행 수명·관측 구간 |
| 가능한 설명 | 열린 트랜잭션이 기다림을 만들었을 수 있음 |
| 아직 모르는 것 | 이 blocker가 전체 지연 증가의 대부분을 설명하는가? |
| 반박할 증거 | 느린 요청 대부분이 해당 DB 호출을 하지 않았음 |
| 다음 확인 | 같은 요청의 DB 구간과 대기 관계를 연결 |

## 이해 확인

1. 상관관계가 보이면 원인을 확정해도 되는가? **다른 설명과 시간·범위의 일치를 확인해야 합니다.**
2. 동일한 이름의 값은 평균을 내서 하나로 합치면 되는가? **모집단·단위·구간·계정이 맞는지 먼저 확인합니다.**
3. 모르는 부분을 남기면 분석이 실패한 것인가? **확인 범위와 다음 증거를 명확히 하는 것이 정확한 분석의 일부입니다.**
4. 실험에서 관측한 한 버전의 결과를 모든 배포판의 보장으로 확장하는가? **적용 버전·설정·실험 경계를 유지합니다.**
