# 숫자가 다를 때: 측정 경계, 시간 구간과 오차

> 상태: 검토됨 · 적용 범위: 측정·집계의 공통 원리, Prometheus·OTel·Linux의 명시된 규약 · 검토일: 2026-10-04 · 계산 입력은 별도 표시한 실제 실습 외에는 가상 예시

## 먼저 이해할 것

두 체중계가 다른 값을 보여 주면 어느 것이 고장인지부터 결정하기 쉽습니다. 하지만 한쪽은 사람만, 다른 쪽은 가방을 든 사람을 쟀을 수 있습니다. 모니터링에서도 숫자를 비교하기 전에 **대상, 포함 범위, 단위, 시간, 계산법**이 같은지 확인해야 합니다. 이름이 CPU 사용률이라고 같아도 이 다섯 조건이 다를 수 있습니다.

이 장을 읽고 나면 “값이 다르다”를 수집 오류, 정의 차이, 시간 차이, 정보 부족으로 나누어 조사할 수 있어야 합니다. 선수 개념은 [시계열](time-series.md)과 [평균·분포](distributions.md)입니다.

## 비교하기 전에 작성하는 작은 표

다음은 **제품 설계용 비교 양식**입니다. 빈칸이 있으면 일치 여부의 판정을 보류합니다.

| 질문 | 관측 A | 관측 B에서 확인할 것 |
| --- | --- | --- |
| 어느 대상인가? | 특정 PID의 한 실행 수명 | 같은 PID뿐 아니라 같은 시작 시각인가? |
| 어디까지 포함하는가? | 프로세스 자체 | 자식·컨테이너·호스트 전체를 포함하는가? |
| 어떤 양인가? | 누적 CPU초 | 현재 비율인지 구간 합계인지 누적값인지 |
| 어떤 시간인가? | 10:00:00~10:00:10 | 같은 창이며 실제 수집 시각도 같은가? |
| 어떤 계산인가? | 차분/실측 경과초 | 외삽·보간·평활화가 포함되는가? |
| 어떤 상태인가? | 정상 수집 | 미지원·접근 거절·오래된 값은 아닌가? |

OpenTelemetry는 데이터 유형과 시간적 집계 의미를 구분하며, 누적값의 시작 시각·불연속·겹치는 입력을 다룹니다. 단위만 바꾸면 모든 원천이 같은 의미가 되는 것은 아닙니다. [OTel metric 모델](https://opentelemetry.io/docs/specs/otel/metrics/data-model/)

## 시간 창이 다르면 정확한 값끼리도 다르다

**가상 예시:** CPU를 하나 사용하는 작업이 60초 중 처음 5초 동안만 실행되고 나머지에는 전혀 실행되지 않았다고 가정합니다.

```text
처음 5초의 평균 사용량 = 5 CPU초 / 5초 = 1 CPU
전체 60초의 평균 사용량 = 5 CPU초 / 60초 ≈ 0.0833 CPU
한 CPU를 분모로 표시한 비율 = 각각 100%, 약 8.33%
```

두 값은 같은 작업을 서로 다른 창에서 요약합니다. 1분 평균은 그 안의 5초 폭주를 보존하지 않습니다. 1분 평균을 1초 간격으로 그려도 원래의 1초 해상도가 생기지 않습니다.

수집 간격과 계산 창도 다릅니다. 15초마다 읽은 표본으로 최근 5분의 증가율을 계산할 수 있습니다. 화면 새로고침 간격을 줄이는 것과 원천 측정 간격을 줄이는 것은 별도 작업입니다.

## 누적 카운터의 두 표본과 rate 함수

**가상 예시:** 누적값이 100에서 220으로 증가했고 실제 관측 간격이 12초라면 단순 차분 결과는 `120/12=10/초`입니다. 설정에 “10초마다 수집”이라고 적혔다는 이유로 12초를 10초로 바꾸면 12/초로 과대 계산합니다.

Prometheus `rate()`는 범위 안의 카운터 증가와 reset을 다루고 범위 경계까지 외삽합니다. 따라서 실제 관측 두 점만 빼는 참조 코드와 모든 입력에서 같다고 요구하면 안 됩니다. `increase()` 역시 범위 길이에 따른 계산으로 정수가 아닌 결과를 낼 수 있습니다. [Prometheus rate·increase](https://prometheus.io/docs/prometheus/latest/querying/functions/#rate)

비교 실험에서는 원시 표본, 평가 시각, 범위 선택, reset 처리, 외삽 여부를 함께 보관합니다. 화면에서 반올림된 결과 두 개만으로 계산 구현의 차이를 판정하기 어렵습니다.

## 시계의 해상도와 정확도

벽시계는 사건이 달력상 언제 발생했는지를 표현하고, monotonic clock은 한 시계 수명 안의 경과 측정에 사용합니다. 프로세스 CPU clock은 프로세스가 사용한 CPU 시간을 측정하는 별도 원천입니다. 같은 “초”라도 측정하는 양이 다릅니다. Linux의 시계별 동작과 조정 특성은 개별 clock 규약을 따릅니다. [clock_gettime](https://man7.org/linux/man-pages/man2/clock_gettime.2.html)

해상도는 구분할 수 있는 눈금에 관한 정보입니다. API가 나노초 단위를 반환한다는 사실만으로 실제 오차가 1ns라는 결론을 내리지 않습니다. 수집 지연, 스케줄링, 가상화, 계정 단위와 서로 다른 읽기 시점도 검토합니다.

[Linux 실습](../host/linux-observation-lab.md)의 최초 기록에서는 MONOTONIC 약 2.000005초 동안 CPU 계정이 212 ticks 증가했고, `CLK_TCK=100`으로 계산한 비율은 약 1.06이었습니다. **MONOTONIC도 주파수 조정을 받으므로 분모 시계가 느리게 흐르면 이러한 비율이 나올 수 있습니다.** 같은 WSL 환경의 [추가 실행 기록](../../labs/results/1.1-linux-clock-r1.json)에서는 단일 스레드 busy 구간의 프로세스 CPU clock/RAW가 약 0.99992–0.99995였고, MONOTONIC/RAW는 약 0.937이었습니다. sleep·idle에서도 시계 속도 차이가 이어지고 adjtimex 조정값과 부합하므로 새 실행의 CPU/MONOTONIC > 1은 분모의 주파수 조정으로 설명됩니다. 원래 1.06 표본에는 RAW·tick 기록이 없어 같은 원인을 소급 확정하지 않습니다. tick을 설정한 주체나 RAW의 외부 정확도도 확인하지 않았습니다.

이는 해당 WSL 환경에서 얻은 관측값입니다. 이를 “단일 실행 흐름이 항상 106%의 물리 연산 능력을 쓴다”는 일반 규칙으로 만들지 않습니다. 수집기는 원천값과 품질 상태를 보존하고, 시계·CPU 계정의 정합성 검사를 별도로 수행할 수 있어야 합니다.

## 없는 표본을 메우면 새 가정이 들어간다

**가상 예시:** 10:00에는 메모리가 100MiB, 10:02에는 300MiB였습니다. 중간인 10:01의 실제 값은 알 수 없습니다. 200MiB를 그리는 선형 보간은 표시 방법이지 새 측정 결과가 아닙니다.

| 처리 | 사용자가 알아야 할 의미 |
| --- | --- |
| 마지막 값 유지 | 과거 관측을 현재 창까지 보여 줌; 새 관측은 아님 |
| 선형 보간 | 양 끝 사이의 변화를 가정함 |
| 0 채움 | 실제 미사용이라는 뜻으로 오해될 수 있음 |
| 빈 구간 유지 | 해당 구간의 관측 불확실성을 드러냄 |

그래프 보간 정책과 알림 평가 정책을 별도로 명세하도록 제안합니다. 화면을 보기 좋게 연결한 선이 자동으로 알림의 실제 입력이 되어서는 안 됩니다.

## 수집 결과를 받아들이는 기준

다음은 **어댑터 수용 기준의 예시**입니다. 모든 원천에 동일한 허용 오차를 강제하는 규정은 아닙니다.

1. 정확한 정수 입력의 단위 변환·차분은 기대값과 일치하는지 확인합니다.
2. 비동기 실제 표본은 수집 구간과 원천 눈금을 고려하고 오차 한계를 설명합니다.
3. 다른 정의의 값은 차이를 허용하는 것이 아니라 서로 다른 지표로 분리합니다.
4. 원인을 설명할 수 없는 차이는 품질 이슈로 남기며 0~100%로 잘라 숨기지 않습니다.
5. 분모·대상 수명·관측 범위가 바뀌면 앞뒤 구간을 무조건 이어 계산하지 않습니다.

## 이해 확인

1. 5초 평균 100%와 1분 평균 8.33% 중 무엇이 틀렸는가? **주어진 가상 부하에서는 둘 다 맞습니다. 시간 창이 다릅니다.**
2. 10초 주기로 설정한 수집이 12초 뒤 완료됐다면 차분의 분모는? **두 표본의 실제 경과 시간과 원천 시간 규약을 확인합니다.**
3. 값의 소수점 자릿수가 많으면 측정 정확도도 높은가? **표현 정밀도와 측정 정확도는 다릅니다.**
4. 예상 범위를 벗어난 값은 잘라 내면 되는가? **원천값을 보존하고 단위·시계·범위·계정 방식부터 조사합니다.**
